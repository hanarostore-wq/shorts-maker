# 쇼핑몰 연동 (공식 API)

발주·주문 처리를 화면 자동화가 아니라 **공식 API**로 한다. 판매자센터 화면은
수시로 바뀌어서 자동화가 자주 깨지는데, 발주·결제에서 그게 깨지면 피해가 크다.

## 구조

| 파일 | 역할 |
| --- | --- |
| `endpoints.ts` | 주소와 경로를 모아둔 곳. **규격이 안 맞으면 여기부터 고친다** |
| `coupangAuth.ts` | 쿠팡 HMAC 서명과 공통 호출 |
| `naverAuth.ts` | 네이버 토큰 발급(캐시 포함)과 공통 호출 |
| `orders.ts` | 주문 조회. 두 쇼핑몰을 같은 모양으로 맞춘다 |
| `fulfillment.ts` | 발주 확인·판매가 변경 (쓰기) |
| `executeAction.ts` | 관문을 통과한 동작을 실제로 실행 |

## ⚠ 실제 API로는 아직 검증되지 않았습니다

이 코드는 자격증명 없이 작성됐습니다. **엔드포인트 경로와 응답 필드명은
공식 문서와 대조해 확인해야 합니다.** 특히 아래는 틀릴 가능성이 있습니다.

- 쿠팡 주문서 조회의 `createdAtFrom` / `createdAtTo` 날짜 형식
- 네이버 `pay-order/seller/product-orders`의 요청 바디 형태와 응답 경로
- 네이버 발주 확인 엔드포인트 이름

규격이 안 맞을 때 **빈 배열을 조용히 돌려주지 않고 예외를 던지도록** 짜여
있습니다. 조용히 0건으로 처리되어 주문을 놓치는 것보다, 눈에 띄게 실패하는
편이 낫기 때문입니다.

## 안전장치

쓰기 동작은 전부 승인 관문(`src/lib/agent/store.ts`의 `gateAction`)을 거칩니다.

**금액은 호출한 쪽이 보낸 값을 믿지 않습니다.** `/api/agent/fulfill`이 실제
주문을 다시 조회해 금액을 계산합니다. 금액을 속여 임계값을 통과하는 일을
막기 위한 것입니다. 주문을 하나라도 찾지 못하면 금액을 "확인 불가"로 두고,
정책 엔진은 이를 임계값 초과와 같게 취급해 사람에게 올립니다.

자동 통과된 경로와 사람이 승인한 경로가 **같은 실행기**(`executeAction.ts`)를
씁니다. 두 경로가 갈라지면 한쪽만 고쳐져 동작이 달라지기 때문입니다.

## 자격증명 없이 시험하기

`COUPANG_API_BASE` / `NAVER_API_BASE`를 모의 서버로 돌리면 서명·관문·실행
흐름을 전부 확인할 수 있습니다.

```bash
COUPANG_API_BASE=http://127.0.0.1:3200 \
COUPANG_ACCESS_KEY=... COUPANG_SECRET_KEY=... COUPANG_VENDOR_ID=... \
npm start
```
